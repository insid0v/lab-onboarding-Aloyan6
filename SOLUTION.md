# Отчет по разбору инцидента «Черная пятница» в системе бронирования ресурсов

## Этап 1. Матрица требований к серверной валидации

| Описание инцидента | Тип требуемой серверной проверки | Конкретное правило |
| :--- | :--- | :--- |
| 1. Бронь переговорной комнаты с датой начала `2026-12-01` и датой окончания `2026-11-01` | Проверка бизнес-логики (Business logic validation) + Проверка формата (Range/Format validation) | `end_date > start_date` и `start_date >= current_date`; формат дат строго ISO 8601 (`YYYY-MM-DD`). |
| 2. Заявка на выдачу `-50` ноутбуков пользователем с возрастом `-5` лет | Проверка диапазона (Range validation) + Проверка типа данных (Type checking) | `items_count > 0` (целое число, `Integer`), `user_age >= 18` (и `user_age <= 120`, `Integer`). |
| 3. Пользователь самостоятельно присвоил себе роль `super_admin` в JSON-запросе | Проверка авторизации/ролей (Authorization) + Защита от Mass Assignment | Игнорировать поле `role` в теле входящего DTO при регистрации/обновлении профиля; менять роль может только текущий `super_admin` через отдельный защищенный эндпоинт. |
| 4. В поле «Комментарий» передан XSS-скрипт `<script>document.location=...</script>` | Проверка безопасности/санитизация (Security/Sanitization) | Экранирование HTML-спецсимволов (HTML-escaping) перед сохранением или рендером; очистка входной строки от тегов `<script>` (санитизация) и установка флага `HttpOnly` для cookie. |

## Этап 2. Чек-лист для ревьюирования Pull Request (API-эндпоинты)

Перед слиянием (Merge) нового или измененного эндпоинта рецензент проверяет код по следующим пунктам (варианты ответа: **Да / Нет / Неприменимо**):

1. **Тип данных:** Все входящие параметры запроса (body, query, path) строго типизированы с помощью DTO/схем валидации, и сервер отклоняет запросы с некорректными типами (HTTP 400)?
2. **Диапазоны значений:** Для всех числовых полей (количество, возраст, лимиты) заданы явные минимальные и максимальные границы, исключающие отрицательные или аномально большие значения?
3. **Бизнес-логика дат:** В коде присутствует проверка хронологической корректности интервалов (дата окончания строго больше даты начала, дата начала не в прошлом)?
4. **Защита от Mass Assignment:** Входящие DTO принимают только разрешенный белый список (whitelist) полей, исключая возможность перезаписи системных атрибутов (например, `role`, `is_admin`, `id`)?
5. **Авторизация (RBAC):** На эндпоинте явно настроена проверка прав доступа (Middleware/Guard), гарантирующая, что пользователь может выполнять действие только в рамках своей роли?
6. **Защита от XSS (Санитизация):** Все строковые поля, которые могут отображаться в интерфейсе (комментарии, названия), проходят санитизацию или HTML-экранирование?
7. **Читаемость и структура:** Логика валидации отделена от бизнес-логики контроллера (вынесена в отдельные валидаторы/пайпы/схемы), а названия правил и переменных понятно отражают их суть?
8. **Обработка ошибок:** При провале любой из проверок API возвращает стандартизированный ответ с кодом `400 Bad Request` или `422 Unprocessable Entity` без утечки стектрейса (stack trace) или структуры БД?
