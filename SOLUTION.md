# Отчет по разбору инцидента «Черная пятница» в системе бронирования ресурсов

## Этап 1. Матрица требований к серверной валидации

| Описание инцидента | Тип требуемой серверной проверки | Конкретное правило |
| :--- | :--- | :--- |
| 1. Бронь переговорной комнаты с датой начала `2026-12-01` и датой окончания `2026-11-01` | Проверка бизнес-логики (Business logic validation) + Проверка формата (Range/Format validation) | `end_date > start_date` и `start_date >= current_date`; формат дат строго ISO 8601 (`YYYY-MM-DD`). |
| 2. Заявка на выдачу `-50` ноутбуков пользователем с возрастом `-5` лет | Проверка диапазона (Range validation) + Проверка типа данных (Type checking) | `items_count > 0` (целое число, `Integer`), `user_age >= 18` (и `user_age <= 120`, `Integer`). |
| 3. Пользователь самостоятельно присвоил себе роль `super_admin` в JSON-запросе | Проверка авторизации/ролей (Authorization) + Защита от Mass Assignment | Игнорировать поле `role` в теле входящего DTO при регистрации/обновлении профиля; менять роль может только текущий `super_admin` через отдельный защищенный эндпоинт. |
| 4. В поле «Комментарий» передан XSS-скрипт `<script>document.location=...</script>` | Проверка безопасности/санитизация (Security/Sanitization) | Экранирование HTML-спецсимволов (HTML-escaping) перед сохранением или рендером; очистка входной строки от тегов `<script>` (санитизация) и установка флага `HttpOnly` для cookie. |

## Этап 2. Чек-лист для ревьюирования Pull Request (API-эндпоинты)

Перед слиянием (Merge) нового или измененного эндпоинта рецензент проверяет код по следующим пунктам (варианты ответа: **Да / Нет / Неприменимо**):

1. **Тип данных:** Все входящие параметры запроса (body, query, path) строго типизированы с помощью DTO/схем валидации, и сервер отклоняет запросы с некорректными типами (HTTP 400)?
2. **Диапазоны значений:** Для всех числовых полей (количество, возраст, лимиты) заданы явные минимальные и максимальные границы, исключающие отрицательные или аномально большие значения?
3. **Бизнес-логика дат:** В коде присутствует проверка хронологической корректности интервалов (дата окончания строго больше даты начала, дата начала не в прошлом)?
4. **Защита от Mass Assignment:** Входящие DTO принимают только разрешенный белый список (whitelist) полей, исключая возможность перезаписи системных атрибутов (например, `role`, `is_admin`, `id`)?
5. **Авторизация (RBAC):** На эндпоинте явно настроена проверка прав доступа (Middleware/Guard), гарантирующая, что пользователь может выполнять действие только в рамках своей роли?
6. **Защита от XSS (Санитизация):** Все строковые поля, которые могут отображаться в интерфейсе (комментарии, названия), проходят санитизацию или HTML-экранирование?
7. **Читаемость и структура:** Логика валидации отделена от бизнес-логики контроллера (вынесена в отдельные валидаторы/пайпы/схемы), а названия правил и переменных понятно отражают их суть?
8. **Обработка ошибок:** При провале любой из проверок API возвращает стандартизированный ответ с кодом `400 Bad Request` или `422 Unprocessable Entity` без утечки стектрейса (stack trace) или структуры БД?

## Этап 3. Архитектурное решение методом WSM (Weighted Sum Model)

### Обоснование весов критериев ($W_j$)
* **Гибкость изменения правил ($W_1 = 0.35$):** Самый высокий вес. Бизнес-правила бронирования (лимиты оборудования, правила пересечения дат) меняются чаще всего. Изменения не должны требовать пересборки БД или правки конфигов шлюза.
* **Надежность ($W_2 = 0.30$):** Критически важно после инцидента, чтобы невалидные данные не попадали в систему в обход фронтенда.
* **TCO — стоимость владения и поддержки ($W_3 = 0.20$):** Команде проще и дешевле поддерживать единую кодовую базу на одном языке, чем дублировать логику в SQL-триггерах и настройках шлюза.
* **Производительность ($W_4 = 0.15$):** Важна для пиковых нагрузок (как в «Черную пятницу»), но современная in-memory валидация в коде занимает доли миллисекунды, поэтому вес ниже остальных.
* *Проверка суммы весов:* $0.35 + 0.30 + 0.20 + 0.15 = 1.0$.

### Матрица принятия решений (оценка по 10-балльной шкале)

| Критерий | Вес ($W_j$) | 1. API Gateway ($X_{i1}$) | 2. Application Layer ($X_{i2}$) | 3. Database Constraints ($X_{i3}$) |
| :--- | :---: | :---: | :---: | :---: |
| **Гибкость изменения правил** | 0.35 | 4 | 9 | 3 |
| **Надежность (защита данных)** | 0.30 | 5 | 8 | 10 |
| **TCO (простота поддержки)** | 0.20 | 5 | 9 | 4 |
| **Производительность** | 0.15 | 9 | 7 | 6 |

### Расчет итоговых баллов ($S_i = \sum W_j \times X_{ij}$)
* **1. API Gateway:** $S_1 = (0.35 \times 4) + (0.30 \times 5) + (0.20 \times 5) + (0.15 \times 9) = 1.40 + 1.50 + 1.00 + 1.35 = \mathbf{5.25}$
* **2. Application Layer:** $S_2 = (0.35 \times 9) + (0.30 \times 8) + (0.20 \times 9) + (0.15 \times 7) = 3.15 + 2.40 + 1.80 + 1.05 = \mathbf{8.40}$
* **3. Database Constraints:** $S_3 = (0.35 \times 3) + (0.30 \times 10) + (0.20 \times 4) + (0.15 \times 6) = 1.05 + 3.00 + 0.80 + 0.90 = \mathbf{5.75}$

### Архитектурный вывод
Победила альтернатива **Application Layer (8.40 балла)**. Валидация на уровне кода микросервиса обеспечивает максимальную гибкость при изменении бизнес-логики и низкую стоимость поддержки (TCO). 

**Рекомендация (эшелонированная защита):** Основную бизнес-валидацию (даты, лимиты, роли, санитизацию) необходимо разместить в **Application Layer**, но усилить ее базовыми ограничениями в **Database Constraints** (`NOT NULL`, `CHECK (count > 0)`, `Foreign Keys`) для защиты целостности данных при прямом доступе к БД, а на **API Gateway** оставить только базовую отсечку невалидного JSON и rate-limiting.

## Этап 4. Актуализация процессов Scrum (Definition of Done)

Для предотвращения попадания подобных уязвимостей в релиз в командный **Definition of Done (DoD)** добавляются два обязательных пункта:

1. **Автоматизированное тестирование негативных сценариев (CI/CD):** Задача не считается выполненной, пока для каждого нового или измененного API-эндпоинта не написаны и не проходят в CI-пайплайне интеграционные тесты, проверяющие граничные значения, отрицательные числа, неверные форматы дат, XSS-инъекции и попытки подмены ролей (покрытие негативных кейсов валидации — 100%).
2. **Обязательное прохождение Security-ревью по чек-листу:** Pull Request может быть влит в основную ветку только после одобрения (Approve) как минимум одним разработчиком (или техлидом) с явным подтверждением в комментариях к PR, что код проверен по актуальному *Чек-листу ревьюирования API-эндпоинтов*.
